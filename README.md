# PupulinBot

云端首次部署、更新及本机数据迁移见 [云服务器部署](CLOUD_DEPLOY.md)。

面向 QQ 群的雀魂助手：基于 **NoneBot2 + OneBot 11**，提供 UID/昵称绑定、牌谱屋查询、群友对局监控，以及可接入自托管 Mortal 的自动复盘和评分卡。项目采用 SQLite，单机即可运行。

> 牌谱数据来自第三方公开索引，通常只覆盖金之间及以上、并可能在结算后才出现；“开局提醒”取决于配置的上游是否返回尚未结束的记录。请合理设置轮询间隔并遵守上游服务条款。

## 功能

- QQ ↔ 雀魂 account ID（常称 UID）绑定，也可以用昵称检索绑定。
- 查询最近牌谱、名次、分数并生成可点击的牌谱链接。
- 四麻/三麻生涯统计（平均顺位、顺位率、和牌、放铳、立直、副露）与群排行；扩展统计不可用时标为“暂无数据”。
- 按群订阅成员；定时发现开局和结算，使用数据库原子去重，多群互不影响。
- 可选实时网关支持真正的结算前开局检测；掉线恢复后按订阅时间、从旧到新检查最近一页四麻结算。
- 显式开启自动分析后，结算牌谱提交 Mortal 服务；手动 `mortal` 命令支持指定座位。
- 将评分、等级和报告链接绘制成适合 QQ 发送的 PNG 卡片。
- Mortal 有界队列、总耗时限制、任务取消处理、服务错误提示、持久化绑定和订阅。
- QQ 通知发送成功后确认，失败可重试；进程中断留下的通知预留在五分钟后可重试。

## 实现范围与后续工作

| 能力 | 当前范围 | 尚需补齐 |
| --- | --- | --- |
| QQ 交互 | NoneBot2 + OneBot 11 命令与群消息 | 真实 QQ 适配器联调；未内置 QQ 登录服务 |
| 绑定 | account ID/昵称查找；歧义时展示 ID 候选 | 账号所有权验证；游戏好友编号与 account ID 的转换 |
| 牌谱/统计 | 四麻最近牌谱；三麻/四麻统计与订阅成员群排行 | 三麻最近牌谱命令与三麻结算订阅、统计时间范围选择 |
| 开局检测 | 可选实时网关客户端 | 雀魂 WebSocket/Liqi 监听器及网关服务本身 |
| 结算提醒 | 四麻轮询、群/成员独立去重、发送失败重试 | 跨页补发、游标持久化、同账号跨群查询复用 |
| Mortal | 同步/异步 HTTP 客户端、手动/自动提交、PNG 评分卡 | 牌谱下载、mjai 转换、模型推理及报告托管服务本身 |
| 自动复盘恢复 | 当前进程内有界队列 | 队列/结果持久化、失败退避、重启恢复及跨群复用 |
| 运维 | Docker、环境变量、SQLite 迁移、错误日志、CI 配置 | 健康检查、自动备份方案与真实对局验收 |

优先完成真实环境联调，再实现持久化补发游标与复盘任务恢复。表中的外部服务均需要单独配置；仅运行本项目不会获得实时雀魂监听或 Mortal 推理能力。

监控通知默认使用两列玩家图片卡片，并保留可点击牌谱链接。卡片显示座风、昵称、牌谱记录段位、结算顺位/得点、PT 增减、此前最多 10 场顺位和和牌/放铳/副露/立直统计条。
统计是生成时的累计数据，不能当作开局时的历史快照；此前顺位只使用该局之前的收录记录。补充查询总预算 120 秒，失败或缺失显示空值，图片生成失败自动降级为文字。
实时开局卡片仅在配置实时源后可用，不根据结算牌谱推测开局。

监控仅处理订阅后开始的对局，重复开启不会重置订阅时间。每轮先查最近 20 场；初次轮询或发现停机期间跨度超过该窗口时，分页补查默认最多 200 场。
恢复正常后回到小窗口查询。超过补查上限时会在 `msstatus` 标明，不能保证更早对局已全部补齐；
管理员可配置 `PUPULIN_MONITOR_CATCHUP_LIMIT`（20–2000），实际下限不会小于页大小。通知采用至少一次投递：QQ 已收消息但数据库确认前进程退出时，恢复后可能重复通知，不保证严格只投递一次。当前设计面向单个 Bot 进程。

牌谱屋兼容实现对照上游的 [牌谱字段及顺位规则](https://github.com/SAPikachu/amae-koromo/blob/master/src/data/types/record.ts)、[统计与请求时间范围](https://github.com/SAPikachu/amae-koromo/blob/master/src/data/source/records/loader.ts)、[模式编号](https://github.com/SAPikachu/amae-koromo/blob/master/src/data/types/gameMode.ts) 与 [统计字段](https://github.com/SAPikachu/amae-koromo/blob/master/src/data/types/metadata.ts)。上游公开接口可用性及访问限制仍须在部署环境验证。

## 快速开始

### 1. 安装

需要 Python 3.11+。本项目遵循 `src` 布局：

```bash
python -m venv .venv
. .venv/bin/activate
pip install -e '.[dev]'
cp .env.example .env
python bot.py
```

也可以执行 `docker compose up -d --build`。将 go-cqhttp、Lagrange.Core 或 NapCat 的 OneBot 11 反向 WebSocket 指向本 Bot 的 `/onebot/v11/ws`；连接鉴权等 NoneBot 环境变量按所使用的实现配置。

### 2. 配置

所有业务变量以 `PUPULIN_` 开头：

| 变量 | 默认值 | 用途 |
| --- | --- | --- |
| `PUPULIN_DATABASE` | `data/pupulin.db` | SQLite 文件 |
| `PUPULIN_PAIPUYA_BASE_URL` | 牌谱屋四麻 API | 可替换为兼容代理/镜像 |
| `PUPULIN_PAIPUYA_SANMA_BASE_URL` | 牌谱屋三麻 API | 三麻兼容代理/镜像 |
| `PUPULIN_PAIPUYA_API_TOKEN` | 空 | 授权 API Key；标准 Bearer，仅发送至指定 5-data API 域名；不要提交到版本库 |
| `PUPULIN_PAIPUYA_AUTO_CAP` | `false` | 配置 Key 时只在确认 Key 失效后启用备用 CAP；无 Key 时保留原 CAP 模式，须安装可选依赖与原生库 |
| `PUPULIN_CAP_WORKERS` | `2` | 原生 HashWX 求解进程数（1–8） |
| `PUPULIN_CAP_TIMEOUT` | `60` | CAP 求解总超时，超时终止求解进程组 |
| `PUPULIN_CAP_CACHE_DIR` | `data/cap` | 私有临时 Token 缓存，不应公开或纳入备份分享 |
| `PUPULIN_HASHWX_LIBRARY` | 空 | 可选兼容原生动态库绝对路径，支持替换 LGPL 实现 |
| `PUPULIN_MONITOR_CATCHUP_LIMIT` | `200` | 掉线补查上限（20–2000），触顶会在状态命令提示 |
| `PUPULIN_MONITOR_INTERVAL` | `60` | 监控周期（秒，最小 20） |
| `PUPULIN_MONITOR_PAGE_SIZE` | `20` | 每次检查最近牌谱数（1–200），目前不跨页补发 |
| `PUPULIN_MORTAL_API_URL` | 空 | Mortal HTTP 桥地址；空时关闭自动分析 |
| `PUPULIN_MORTAL_API_TOKEN` | 空 | 可选 Bearer Token |
| `PUPULIN_MORTAL_TIMEOUT` | `180` | 从提交到轮询完成的总超时（秒），不含本地排队时间 |
| `PUPULIN_REVIEW_WORKERS` | `1` | 并行分析数量 |
| `PUPULIN_REVIEW_QUEUE_SIZE` | `20` | 等待队列容量（不含正在分析的任务），满时返回繁忙提示 |
| `PUPULIN_LIVE_API_URL` | 空 | 可选实时状态网关，配置后启用结算前开局提醒 |
| `PUPULIN_LIVE_API_TOKEN` | 空 | 实时网关 Bearer Token |

主通道使用维护者授权的 API Key；有效 Key 不运行以下旧方式。
以下仅为 Key 确认失效时的可选备用安装说明。在已激活的虚拟环境中运行：

```bash
pip install -e '.[cap]'
python -m pupulinbot.cap_worker --build
# 在 .env 中设置 PUPULIN_PAIPUYA_AUTO_CAP=true，然后重启 Bot
```

构建需要 C11 编译器（macOS 的 Command Line Tools，Linux 的 build-essential），
CMake 由 `cap` 可选依赖提供。原生库保存在 `data/hashwx`，不会在收到群消息时编译。
三麻和四麻共享 Token 与刷新锁；Token 按服务端有效期私有缓存到 `data/cap`，
进程重启后可复用。CAP 在独立进程中运行，默认 2 个计算工作进程、60 秒总超时，
失败后暂停 60 秒。普通 429 按 `Retry-After` 暂停；无 Key 模式的401/403不触发求解。
有 Key 时只在HTTP401或明确的Key无效/过期响应后启用此备用；普通403、429及网络错误不触发。
适配器包含对 CAP instrumentation 的模拟；站点协议变化可能导致失败，
不能将一次成功视为长期可用或无限访问授权。原生 HashWX 使用 LGPL-3.0-or-later，
来源及改动见 `src/pupulinbot/_cap/ORIGIN.md`。默认 Docker 镜像未启用 CAP 构建工具。

### 3. Mortal 桥接协议

Mortal 及雀魂日志转换器通常需要较大的模型和独立运行环境，因此 Bot 使用小而稳定的 HTTP 边界，可对接已有 Mortal/akochan-reviewer 部署或自行写适配器：

```http
POST /review
Authorization: Bearer <optional token>
Content-Type: application/json

{"url":"https://game.maj-soul.com/1/?paipu=...","seat":0}
```

成功响应：

```json
{"status":"done","rating":87.52,"rank":"A","url":"https://review.example/result/123"}
```

桥接服务负责下载牌谱、转换为 mjai、调用 Mortal，并返回汇总指标；这样不会把特定模型版本、GPU 配置或非稳定的雀魂私有协议耦合进 QQ Bot。`seat` 可以为 `null`。错误可返回 `{"status":"error","error":"原因"}`。

也支持异步分析服务：首次响应可使用 `{"status":"queued","status_url":"/jobs/1"}`，Bot 会每两秒查询一次，直到返回 `done`、`error` 或达到配置的总超时时间。`status_url` 支持相对路径或与配置服务同源的绝对地址；跨域地址被拒绝，避免将鉴权 Token 转发给其他服务。成功响应必须包含有限数值的 `rating` 或 `score`，缺少评分或未知状态会报告错误。

### 批量 Mortal 复盘（1–100 场）

群内绑定后使用 `mortal batch 20`，选取本人最近 20 场四麻半庄（金南／玉南／王座南）。
`mortal status <任务编号>` 查看结果；`mortal report <任务编号>` 直接发送折线图到群内，
无需下载文件。图片采用四项汇总卡片、Rating 与连续五场均线主图，
AI 一致率、5%／10% 恶手率分别展示，标明对局日期范围和完成进度；
未复盘／失败场次留空，不同模型分开绘制，不连接缺失区间。
只有一场结果时显示单点并注明无法形成趋势。
需要完整 HTML 表格时使用 `mortal file <任务编号>`。
表格含时间、房间、顺位、模型、Rating、一致率、5%／10% 恶手率、决策数和报告链接。
Rating 按成功场次计算平均／中位数；一致率按决策数加权；缺失值不当作零，
不同模型与温度分组统计。评分不能跨模型比较，也不等同于棋力。

配置兼容的 `PUPULIN_MORTAL_API_URL` 后，批量任务使用 `PUPULIN_REVIEW_WORKERS`
控制并发（默认 1，最多 4）。分析结果先保存，昵称与名次核验单独排队，
不会占用浏览器或分析服务的工作槽；最终报告仍需通过昵称核验。
遇到服务失败立即暂停，不向故障服务连续发起剩余任务；
`mortal pause <任务编号>` 停止继续提交，已在外部执行的任务可能仍会完成；
`mortal resume <任务编号>` 可跳过成功项继续。任务和原始导入报告保存在
`PUPULIN_BATCH_DIRECTORY`（默认 `data/batches`），重启后可手动继续。
正常完成时仅发送结果图片，不再另发“完成 X/X 场”文字；异常、重试等状态保留提示。结果图生成或发送失败时会提示已保存结果及重新查看命令。
群文件通过 `base64://` 传输（最大 2 MiB），需要 OneBot 服务端支持该格式；
本机 NapCat 已支持，无需让 QQ 沙箱读取 Bot 项目目录。

启用 Chrome 在线引擎后，Bot 使用一个浏览器逐项提交和读取报告，保存每场原生 JSON，最后自动发送折线图。
桥接服务已配置时优先使用桥接服务；否则使用在线引擎。安装与配置：

```bash
pip install '.[online]'
```

```dotenv
PUPULIN_MORTAL_ONLINE=true
PUPULIN_MORTAL_BROWSER_PROFILE=data/mortal-chrome
PUPULIN_MORTAL_ONLINE_MODEL=4.1b
PUPULIN_MORTAL_ONLINE_COOLDOWN=20
PUPULIN_MORTAL_ONLINE_TIMEOUT=600
```

采用本机 Downloads/batchmortal 最新版的 BrowserAutomator（MIT），源文件及哈希记录在
`src/pupulinbot/_batchmortal/ORIGIN.json`，Bot 队列和恢复逻辑通过独立适配器连接。
SeleniumBase 采用 `uc=True`，默认 `PUPULIN_MORTAL_ONLINE_HEADLESS=true`。
Linux 后台运行按原项目转为 Xvfb 虚拟显示；macOS 保持真正无头模式，但 GUI 验证点击
可能不可用，不能保证获得验证 Token。首次启动可能下载匹配的 ChromeDriver。
使用独立持久化配置目录，不读取个人 Chrome 配置。

`PUPULIN_MORTAL_ONLINE_COOLDOWN` 设置两次提交的最短间隔（默认 10 秒）。
旧配置中的 `PUPULIN_MORTAL_ONLINE_CONCURRENCY` 已停用。
暂停或重启后先恢复已提交的场次。旧浏览器目录里的结果可从本机报告或已保存的远端地址读取，
尚未提交的场次会由当前浏览器继续处理。
网络、浏览器异常或服务任务超时会自动按30/60/120/240/300秒退避恢复，最多5次；
恢复计划保存在任务文件中，每15秒检查，重启后仍有效。优先按已保存的报告或进度页地址
只读找回结果，核验座位和模型后继续；未知提交不重复发送。
提交前网页验证超时会用相同配置重开 Chrome 并静默重试。同一份牌谱的各座位共用三次静默重开机会。
用完后才通知并挂起，1 分钟后续跑；同一牌谱可挂起两次，仍失败时保存进度并停止。
人工暂停、明确验证失败及限流需要手动继续。

在线跑谱完成后，原始报告按“牌谱来源＋牌谱 ID＋座位＋模型”缓存到任务目录旁的
`mortal-cache`（默认 `data/mortal-cache`）。移除任务或重启 Bot 后仍可复用，同样的分析无需启动浏览器。
读取缓存会校验报告的座位、模型和指标。旧任务中的报告可校验后迁入缓存。
手动指定场次导入的报告因无法自动确认与牌谱对应，保存在原任务中。


其他配置：`PUPULIN_MORTAL_ONLINE_RETRIES=2`（仅提交前准备失败重试），
`PUPULIN_MORTAL_TURNSTILE_TIMEOUT=120`、`PUPULIN_MORTAL_ONLINE_PROXY`，
`PUPULIN_MORTAL_SAVE_HTML=true`、`PUPULIN_MORTAL_SAVE_SCREENSHOT=false`。
提交前持久化提交记录；提交后超时先检查原页面，不重复 POST。
若重启丢失会话，优先从保存的报告地址恢复；没有地址时需要找回报告并导入。
仅当服务器正文明确为 `invalid captcha response` 时记为拒绝接受，允许稍后重试；
其他提交后异常继续保留待核对状态。表单、验证 Token、报告均保留显式等待；页面采用 `page_load_strategy=none`，
普通表单提交通过零延迟定时器异步触发，避免 WebDriver 在页面跳转上阻塞 120 秒。
不额外等待所有页面资源达到 complete，避免慢资源拖延导致 Token 过期。
控制连接的单次读取上限为 30 秒，已完成提交日志可直接读取本机 JSON 恢复，
并持久化已观察到的作者进度／报告地址。拿到报告地址后，查看器两秒仍未就绪时，
可后台只读下载已有 JSON，严格核对座位、模型和压缩前后指标。
原生报告采用 IPv4 直连，连接等待15秒、单次读取等待60秒，避免慢下载被过早中断。
若读取失败，继续任务会先按已知地址重读，成功前不重新提交牌谱。
停止任务不会撤销外部已提交的复盘。

`mstable <雀魂/天凤链接>` 或 `mortal table <雀魂/天凤链接>` 分析同桌四个座位，分别核对报告座位；
`mortal links <链接1> <链接2>…` 导入 1–100 条链接（默认座位 0）。
四人报告直接发结果表图片，历史批跑仍发折线图。
`mortal export <任务编号> [csv/xlsx]` 按本地 batchmortal 列定义导出；
XLSX 依赖包含在 online 安装项中。导入链接未知的时间、房间等信息保持空白。
原生 JSON、可选 HTML 和截图保存在本机。恶手率沿用本地源码定义：
`is_equal is False` 且实际动作概率 ≤5%／≤10% 的次数除以总检讨数；
无法解析的动作单独计数。不同模型、温度、统计口径分别汇总，四名玩家不会合并平均。

未启用任何分析引擎时只建立任务；也可逐场在线复盘后使用
`mortal import <任务编号> <场次编号> <报告链接>` 导入结构化结果。
导入限制作者域名、核对座位并保存 JSON；报告没有原对局 UUID，手动导入对应场次依赖用户指定。
在线引擎通过当前场次的浏览器提交关联报告，仍核对报告座位。

查询短时缓存只保存成功结果：账号解析最长 300 秒、统计 60 秒、历史图表数据 30 秒。
每个模式最多 64 个缓存条目；超过 200 场的历史查询不进入缓存，同一请求并发时合并加载。
过期或失败数据不会作为成功缓存返回，监控使用独立的新鲜数据查询路径。
网络连接失败及 HTTP 502/503/504 最多重试一次，HTTP 401/403/429 不按普通故障重试。

`msstatus` 查看本群有效监控、最近轮询/成功时间、补查是否触顶、

状态写入失败不会阻止其他群的通知处理。真实开局源未配置时会明确显示该边界。

### 4. 实时开局网关协议

公开牌谱索引通常只能在结算后发现牌谱。若要获得真正的开局提醒，可接入已有的雀魂实时状态服务，并配置 `PUPULIN_LIVE_API_URL`：

```http
GET /players/{account_id}/current-game
Authorization: Bearer <optional token>
```

未在对局时返回 `404` 或 `{"playing":false}`；对局中返回：

```json
{
  "playing": true,
  "uuid": "game-uuid",
  "mode": "四人南",
  "started_at": "2026-09-21T08:00:00Z",
  "players": [{"account_id": 123, "nickname": "雀士"}]
}
```

这一接口边界可以适配基于雀魂 WebSocket/Liqi 协议的开源监听器，而无需让 QQ Bot 保存雀魂账号密码。本仓库未提供监听器实现。未配置时提供牌谱屋三麻/四麻结算监控，不发送真实开局提醒。索引里的未结算记录不作为实时开局证据。

## 牌谱屋授权访问与速率规范

主通道为 `https://5-data.amae-koromo.com/api/v2/pl4` 和同域 `/api/v2/pl3`，
私有 `.env` 的 `PUPULIN_PAIPUYA_API_TOKEN` 作为 `Authorization: Bearer <key>`；
有效 Key 模式不发送 `X-Cap-Token`，不运行 CAP，也不跳转其他域名。
Key 模式会校验 HTTPS、指定主机与API路径，HTTP重定向不跟随，防止凭据外发。

所有实际 GET（含请求重试与切换备用后的请求）共用 SQLite 请求时钟，发送起点至少间隔1.05秒，
没有突发额度；三麻、四麻、监控、图表补充资料和同时运行的本地脚本均共用默认文件
`data/paipuya-rate.sqlite`。可用 `PUPULIN_PAIPUYA_RATE_LIMIT_FILE` 指定共同文件；所有实例必须一致。
缓存命中不计网络请求。429遵守服务端冷却，不通过切换旧通道规避限流。

只有HTTP401，或HTTP400/403的JSON明确报告 `invalid_api_key`、`expired_api_key`、
`invalid_token`、`token_expired` 才确认Key失效；`PUPULIN_PAIPUYA_AUTO_CAP=true` 时允许启用原生CAP备用。
普通403（可能为IP/权限限制）、429、网络断连、超时与5xx均不触发备用。
备用状态仅在本进程生效，配置中的Key不被改写；重启或更新Key后重新优先使用Bearer。
`msstatus` 可查看当前鉴权模式和全局限速，不显示密钥。

监控卡片的四麻标签另按和牌率、放铳率的六档交叉表计算，雀魂与天凤使用同一套规则；区间边界计入较高档，缺失数据不显示，三麻不套用。

## 四麻牌风模型

`msstyle [玩家] last=100 [room=玉南]` 返回牌风坐标图与全部12项模型输入，默认最近100场。
`ms`、`ms4 玩家 -l 100 -r 玉南` 和 `ms4 玩家 -i -l 100 -r 玉南` 显示相同房间、相同样本的牌风；
`ms`/`msstats` 的累计资料、个人面板及监控卡片则显示累计牌风，明确标识口径。

指标为和牌率、放铳率、副露率、立直率、默胡率、平均打点、平均和牌巡数、平均铳点、
流局听牌率、立直巡目、先制率、追立率。率保持 API 的0–1单位，显示时才转为百分比。
默胡率对应牌谱屋 `默听率`（门清默听和牌局数/和牌局数），不是所有默听局占比；
先制率和追立率的分母都是立直局数。

完整12项才分类，不补零、不用累计数据填充最近N场；区间统计的场数必须与已结算样本一致。
三麻不套用，`msstyle mode=3` 会提示不支持。样本小于100战会在完整牌风报告/文字评价中提醒波动。
强度只是离参考均值的距离，不是实力或可信度评分；该页面未提供模型训练群体及有效性验证信息。
原模型只有一个主分类和偏离强度，没有“绝好调”“防守大师”“火龙果”等额外称号。

公式采用独立 Python 实现，对照网页 JavaScript 的29组离线结果（含四位真实玩家）验证，
保留严格阈值、分区边界及零轴的原始行为。源码快照摘要见 `STYLE_MODEL.md`。

### 天凤监控（第一阶段）

- `thwatch on <天凤昵称>`：负责人为当前群添加监控，不使用天凤私密登录 ID。
- `thwatch off <昵称>`：负责人移除本群监控；`thwatch off all` 清空本群。
- `thwatch list` / `thwatch status` / `thstatus`：所有成员可查看本群名单与数据源状态。
- `thlast [昵称]`：最近一场结果；本群仅监控一人时可省略昵称。

天凤与雀魂统一由 `PUPULIN_MONITOR_OWNER` 指定的 QQ 管理名单；群主、管理员和其他成员均不能增删。旧名单保留，负责人可管理此前任何人添加的本群条目，各群独立。

`help` 合并消息中已加入天凤章节。天凤和雀魂的绑定、订阅独立，不会自动向其他群开启。
每分钟检查一次；重复开启保留起点。每群最多监控 10 位天凤玩家。

来源为 nodocchi 自身使用的公开接口：`/s/wg.js`（观战列表）、
`/api/listuser.php?name=…&start=…`（历史）、
`/api/phoenix_status.php?all=1&username=…`（鳳凰统计）。
独立 HTTP 客户端不携带牌谱屋 API key；串行请求间隔至少 1.1 秒，缓存并复用同一玩家查询。
本机使用 IPv4；连接或读取超时仅重试一次，第二次使用站点的 www 域名。
公开观战通常约 5 分钟延迟，只覆盖来源列出的可观战桌；不需要登录天凤账号。
观战快照 Last-Modified 超过 10 分钟时暂停开局播报并显示异常，空响应同样视为错误。
结算必须等历史实际收录，不会以观战列表消失推断结算。

开局采用三/四人座位卡，展示段位、R、最近十场顺位、本段/段位战战数、鳳桌战数，
以及鳳凰累计和/铳/副露/立直、局收支、和铳差、鳳凰安定段。
PT、最高段位和最近十次段位变化按完整公开历史推算；只有推算的当前段位与观战一致时显示，
卡片标 `PT*`，并在脚注说明推算来源。不是游戏直接返回的 PT；历史缺漏可能影响推算。
历史按开局时间截断，避免该场结算泄露到开局卡片。天鳳位不显示普通 PT。
统计与百分位按桌型对应 s4_1/s4_2、s3_1/s3_2，东风与半庄不混用。
百分位来自 `/s/phoenix_scale_all.js` 同模式、同桌型的量化分布，仅在玩家达到分布的最小战数时显示；
条内数字是原始数值的经验百分位，**不是实力排名**，例如铳率百分位越低，表示铳率越低。
标签是本项目公开规则推断，不声称复刻示例 Bot 的未公开算法；缺失统计为 `—`。

标签规则：最近十战齐全，四麻平均顺位≤2.0/≥3.0为好调/低迷，三麻阈值为≤1.6/≥2.4；
近30天至少三次段位变化且最近五次变化均在六段以上，标段位起伏。
四项百分位齐全时按优先级：和≥80且铳≤30为攻守兼备；铳≤10且和≤35为铁壁地藏；
和≤40且铳≤40为谨慎运营；副露≥80为副露进攻；立直≥80为立直进攻；其余为标准运营。
这些描述只反映所用累计/近期数据，不套用雀魂四麻12指标模型。

资料查询最多两个请求并行等待响应；首次完整历史另设一个通道，避免挤占统计和观战查询。所有通道共用至少1.1秒的请求发起间隔，完全相同请求共享结果；
分布缓存一天、统计15分钟，有效期内的缓存可跨进程重启复用。完整历史首次后台加载，单次完整响应上限180秒，
成功后写入专用历史缓存；后续只查询最近已知记录前两小时以来的增量并合并去重，
不再反复下载数 MB 的全部历史。内存最多16份历史、磁盘最多64份 SHA256 命名的历史缓存；
订阅不受缓存清理影响。增量失败时不将旧缓存冒充本轮已更新的PT。
开局补充资料等待上限180秒，部分结果即时保留；不完整图片仅缓存10秒，后续请求可补齐；完整图片缓存10分钟。卡片超时不取消首次历史后台加载。
已订阅玩家的历史会提前在后台预热。统计默认优先使用本机实测更快的 www 域名，连接失败再换另一域名。
进程重启后可继续使用磁盘历史并补齐增量。

结算显示北京时间、来源记录的分钟时长、玩家和牌谱链接。
标准四麻段位战根据 nodocchi 规则表（30000 返、含 oka 的顺位分 40/10/-10/-20）
从结算点还原持点，并检查总计 100000 和排名顺序。三麻、赛事和特殊规则不做这种还原，
明确显示“结算点（含顺位分），非最终持点”。公开记录没有牌谱 URL 时明确说明缺失。

订阅、开局待发送队列和通知去重持久保存在 SQLite；同群同场只播报一次，各群互相独立。
发送失败保留待重试事件；崩溃遗留的发送租约到期后重试。
新订阅跳过开启前已经结束的历史，结算查询保留两小时重叠区间处理延迟收录和短暂掉线。
公开时间只有分钟精度，开启时仍在进行的对局会正常结算播报。
真实未来对局的开局到结算闭环仍需要实战验收。


### 牌谱屋慢响应与等待

`PUPULIN_PAIPUYA_TIMEOUT=60` 控制单次网络读取等待（原默认 15 秒）。
连接建立最多等待 20 秒，读取最多等待 60 秒；连接/读取失败或 502/503/504
限速重试一次，每一次重试都重新通过同一个跨进程 1 QPS 闸门。
完整单次响应还受 90 秒时限保护，避免服务器持续慢速发送导致永久挂起。
等待 QPS 排队不计入网络超时。部分统计补充查询的外层等待从 25 秒提高到 210 秒。
429 仍遵守 Retry-After；普通超时不会触发 CAP 备用或改换 API 域名。
日志区分连接与读取超时，记录尝试次数和耗时，不记录 Bearer 密钥。


### 雀魂官方观战源

设置 `PUPULIN_SPECTATOR_BROWSER=true`，安装已有 `online` 可选依赖后重启 Bot。
Bot 打开独立 Chrome 雀魂窗口，用户自行登录；登录资料由该浏览器配置目录
`data/majsoul-spectator` 保存，不将密码或令牌写入 Bot 配置。
如同一账号不支持同时在线，使用用于观战的账号登录该窗口。
该功能不会读取或修改雀魂 App；通过浏览器已建立的官方 WebSocket 发送只读观战请求，不读取登录载荷或存储。既有 `PUPULIN_LIVE_API_URL` 如有配置则优先使用。

登录后自动读取官方 `fetchGameLiveList`，覆盖四麻/三麻金、玉、王座东西场。
每次 RPC 至少间隔 1.05 秒，扫描结果共享缓存 30 秒；原监控轮询周期不变。
`ms4 <玩家> -o` 查询公开观战，`ms4 <玩家> -o -i` 返回开局卡片；三麻使用 `ms3`。
`mswatch` 管理本群结算名单，`msstatus` 显示数据源状态。
只匹配公开列表实际返回的玩家，不将“未找到”视为离线或结算；结算仍使用牌谱屋。
接口扫描失败会显示错误，不把失败缓存为空列表。浏览器关闭后需要重启 Bot。
尚需在本机登录后验收真实列表与开局播报，不保证覆盖所有对局或即时出现。

监控图片等待：雀魂资料加载最多120秒，生成阶段最多150秒；天凤资料加载最多180秒，常规数据请求每次最多60秒。QQ发送接口最多等待90秒，与生成阶段分别计时。发送失败仍会释放通知预留，供后续轮询重试。

`PUPULIN_MONITOR_NOTIFY_START=false` 全局关闭雀魂三麻及四麻开局提醒，保留原有结算通知，不影响天凤监控或手动观战查询。

Mortal 支持雀魂与天凤四麻半庄牌谱：`mortal <天凤链接> [座位0–3]`、`mstable <天凤链接>` 和 `mortal links <链接1> <链接2>…` 共用在线跑谱、重试及图片报告流程。天凤链接中的 `tw` 为默认座位，显式指定的座位优先；无 `tw` 时为0。支持普通 http/https 官方天凤回放链接及 log 编号，内部统一为 HTTPS。多链接按来源、牌谱与座位去重，导出来源区分 tenhou/majsoul；最近N场昵称批跑仍使用雀魂账号。

Mortal表格优先显示原始牌谱的座位昵称：天凤读取官方XML的UN字段并解码；雀魂最近N场任务保留牌谱屋原始昵称；导入链接优先使用本地已收录对局和历史任务，缺失时解码牌谱视角、按日期从标准 Bearer API 检索，并严格匹配原牌谱 UUID 和座位。补昵称共用现有 1 QPS 限速，不重新分析；无视角且未被收录的链接仍可能无法补齐。查看旧报告时可补齐昵称，无需重新分析。查看器的A/B/C/D匿名占位名不作为真实昵称。天凤报告及导出要求真实座位昵称全部就绪；读取失败自动重试并保存独立的昵称恢复计划，不重新跑谱。尚未读取完整时不输出占位报告。雀魂无法核实的昵称仍显示—。

一番街使用 `mstable dboqr0kj4ak3gig8n0tg@0` 分析整桌四个座位，或 `mortal dboqr0kj4ak3gig8n0tg@2` 分析指定座位；显式座位参数优先于 `@` 后缀，省略后缀默认为 0。`mortal links` 也可混合雀魂、天凤和一番街输入。一番街使用作者页面的 Riichi City ID 字段，支持四麻半庄；座位昵称通过 [CityLogs 公开转换 API](https://rc.honk.li/api) 按原始 ID 严格匹配，最终名次从已完成报告的 MJAI 终局数据恢复。该读取不使用牌谱屋 Key，也不触发额外跑谱。

天凤XML读取使用明确的PupulinBot User-Agent，HTTP 200空正文按下载异常重试；读取失败记录异常类型与牌谱编号。已核验原始昵称可从同来源、同牌谱编号的历史任务恢复，重启后无需重复下载。昵称补齐保持人工暂停状态，不启动分析或自动恢复。

雀魂名单按群号及三/四麻独立保存，统一由 `PUPULIN_MONITOR_OWNER` 管理。
升级前已开启的订阅原群保留，不复制到其他群；天凤名单保持独立。

### 受限群与二级会员

`PUPULIN_MONITOR_ONLY_GROUPS` 指定受限群。群内普通成员可以绑定、解绑、查询雀魂和天凤，
以及使用 `help`。二级会员还可以使用 `mortal`、`msmortal`、`mstable`、`mortalstatus`
和相关别名，按现有规则管理自己在原群创建的任务。
监控命令 `mswatch`、`thwatch`、`msstatus`、`thstatus` 在受限群只向负责人和超级管理员开放。
各群已配置的监控正常播报，增删监控对象仍由 `PUPULIN_MONITOR_OWNER` 负责。

二级会员白名单按 QQ 账号全局生效，存入 SQLite。只有 `SUPERUSERS` 指定的 Bot 超级管理员可以操作：

- `vip2 add <QQ号或@群友>` 添加。
- `vip2 del <QQ号或@群友>` 移除。
- `vip2 list` 查看。

二级会员没有监控或白名单管理权限。普通群的普通成员沿用原有命令规则。
新群名单默认留空，各群名单保持独立，不自动复制。

结算播报会在检测到升段时追加“欢迎新<段位>”。雀魂只核对该场、该模式的段位与积分变化，
不拿当前总统计推断历史升段；天凤按 nodocchi 完整公开历史的 PT 规则计算该场升段，
排除账号重置和人工 PT 调整。数据不全或核对超时仍正常播报结算，不追加祝贺。
祝贺和结算共用同场去重，重启不会重复发送，也不追补已播报的旧局。

Mortal 全桌图片按最终名次排列，依次显示游戏昵称、最终名次、Rating、一致率和两档恶手率；
移除起始座位和模型列。最终名次优先取原牌谱结果，雀魂读取牌谱屋结算分数/顺位，天凤读取原始 XML 的终局结果；缺失时可从 Mortal 原生报告的完整 MJAI 终局数据恢复（计入立直棒和结算分数），与昵称查询独立。银之间不在当前牌谱屋收录范围，匿名报告无法恢复真实昵称。
不会由 Mortal 评分推断。Rating 大于 90 时统一显示带渐变高光、柔光和星芒的亮金色，90 及以下保持默认颜色，不设红色档。

超级管理员通过 NoneBot 的 `SUPERUSERS` 配置指定，例如 `SUPERUSERS=["285843647"]`。
超级管理员可在所有群（包括仅监控群）使用全部有效命令、替群友绑定雀魂、管理任何 Mortal 任务。
超级管理员和二级会员在受限群创建的 Mortal 任务会正常发送进度及结果。
权限例外不改变各群独立的监控名单，也不放宽数据验证或 API 限速。
